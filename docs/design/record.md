# record: Public WebSocket の板と約定を記録する

## 結論

- `coincheck record` は Coincheck の Public WebSocket を購読し、受け取ったメッセージを gzip の JSONL に書く。メッセージの中身は変えない (行を 1 行に保つための改行の置き換えだけをする)
- 板の WebSocket は差分しか送らないので、REST の板 (`GET /api/order_books`) も接続のたびと 60 秒ごとに取り、別の stream に書く。差分だけでは板を組み立てられないため
- 1 行は `{"recv_at":"<受信時刻 ISO 8601 UTC>","msg":<受信した JSON の生テキスト>}`
- ファイルは `<out>/<stream>/<pair>/<UTC 日付>T<HHMMSS.mmm>Z.jsonl.gz`。`<stream>` は `trades` / `orderbook` / `orderbook_snapshot`。時刻は、そのプロセスがその日その stream で最初に受け取ったメッセージの受信時刻。プロセスを起動し直すたび、日付が変わるたびに新しいファイルになり、既にあるファイルには書き足さない
- 1 つのファイルには、flush のたびに完結した gzip のメンバーを 1 つずつ追記する
- 1 日分を読むときは、その日付で始まるファイルを名前順に 1 つずつ展開する (`for f in data/orderbook/btc_jpy/2026-10-18T*.jsonl.gz; do zcat "$f"; done`)。`zcat` に複数ファイルを一度に渡すと、末尾の壊れたファイルで止まり、後ろのファイルを読まない。壊れた末尾は改行で終わらない途中の行を出すことがあるので、ファイルごとに改行で終わらない最後の行は捨てる
- 切断と無通信は再接続で回復する。書き込みに失敗したら exit 1 で止まり、再起動は外 (systemd 等) に任せる
- 書き方 (ファイルの切り方・gzip のメンバー・排他作成・回復) は gmocoin-cli の `docs/design/record.md` と同じにしてある。違うのは購読の形、受け付けるメッセージ、板のスナップショットの 3 つ

## 使い方

```bash
coincheck record                                   # btc_jpy の orderbook と trades を ./data に
coincheck record --pair btc_jpy --pair eth_jpy --out /srv/coincheck/data
```

- `--pair` (複数可、既定 `btc_jpy`): `^[a-z0-9_]+$` 以外は拒否する
- `--channel` (複数可、既定 `orderbook` と `trades`): この 2 つ以外は拒否する
- 引数の拒否は接続する前に行い、exit は 0 以外
- `--out` (既定 `./data`)
- 購読は `--pair` × `--channel` の全組み合わせ (重複は 1 つにする)
- SIGINT / SIGTERM で溜まっている分を書いてから exit 0
- 想定していない例外 (uncaughtException / unhandledRejection) は stderr に出して exit 1
- 接続先は環境変数で上書きできる。WebSocket は `COINCHECK_PUBLIC_WS_URL` (既定 `wss://ws-api.coincheck.com`)、REST は `COINCHECK_API_URL` (既定 `https://coincheck.com`)

## 実データの形 (2026-10-18 に観測、btc_jpy)

- 購読コマンドは `{"type":"subscribe","channel":"btc_jpy-trades"}` / `{"type":"subscribe","channel":"btc_jpy-orderbook"}` (公式ドキュメント)。1 コマンド 1 チャネル。購読の応答は来ない
- `orderbook`: `["btc_jpy",{"bids":[["<価格>","<数量>"],...],"asks":[...],"last_update_at":"<unix 秒>"}]`。前回からの差分で、数量 `"0"` はその価格の注文が無くなったことを表す。90 秒で 248 件 (約 2.8 件/秒)。板の外側の遠い価格の変化も届く
- `trades`: `[["<unix 秒>","<約定 ID>","btc_jpy","<価格>","<数量>","<buy|sell>","<taker の注文 ID>","<maker の注文 ID>",<板寄せの注文 ID か null>],...]` の 2 次元配列。0.1 秒ごとにまとめて届く (公式ドキュメント)。90 秒で 7 件の時間帯と、120 秒で 1 件の時間帯があった。taker の約定 (と板寄せ) だけが届き、`order side` は taker 側
- REST `GET /api/order_books?pair=btc_jpy`: `{"asks":[["<価格>","<数量>"],...],"bids":[...]}`。上下 200 本ずつで、時刻は含まない。`cache-control: max-age=0, private` (再利用するなら再検証が要る) で、3 秒あけた 2 回の取得で中身が違った。存在しない pair は 400
- 価格・数量は文字列で届く。記録は受信したテキストをそのまま残すので、数値への変換も再シリアライズもしない

## 板のスナップショット

- `orderbook` を購読している pair ごとに、REST の板を取って `orderbook_snapshot/<pair>/` に書く。行の形は WebSocket と同じで、`msg` は応答の本文、`recv_at` は応答を受け取った時刻
- 取るのは、接続を開いて購読コマンドを送った直後と、`snapshotIntervalMs` (既定 60000) ごと。再接続で差分が途切れても、次の接続の最初に取り直すので、組み立て直せない時間は再接続の間と応答が返るまでに収まる
- 同じ pair の前の取得が終わっていなければ、その回は取らない (応答が遅いときに取得が積み上がらないように)
- 取得は接続が開いている間だけ始める。取得の間に接続が切れていたら、その応答は差分が途切れた前後にまたがった板かもしれないので書かずに捨てる。繋がり直していればすぐ取り直し、切れたままなら次に開いたときに取る (失敗した場合も同じ)。書かれたスナップショットは、どれも 1 つの接続が開いている間に要求して受け取ったもの
- 1 回の取得は 10 秒で打ち切る
- 失敗 (接続できない / 打ち切り / 200 以外 / 本文が `asks` と `bids` の配列を持つ object でない) は stderr に 1 行出して、その回を捨てる。記録は止めない。stats でその stream の数が増えないことで気づく
- スナップショットは WebSocket の無通信の判定にも、再接続の待ちの戻しにも使わない (WebSocket が止まっていても REST は返るため)
- スナップショットの中身がサーバーでいつ作られたかは分からない。分かるのは、要求を送ってから応答を受け取るまで (最長で打ち切りの 10 秒) のどこかということだけ
- 読む側は、スナップショットが来るたびに板を置き直し、その `recv_at` より後に受けた差分を受信順に当てる
- スナップショットの中身は要求を送ってから応答を受け取るまで (最長 10 秒) のどこかで作られたもので、その間に受けた差分の一部が入っていないことがある。入っていない変化は、その価格の次の差分か次のスナップショット (60 秒ごと) で戻る
- `recv_at` より前の差分を当て直す読み方はしない。再接続の直後には必ずスナップショットを取るので、当て直す範囲に切断より前の差分が入り、切断の間に変わった価格を古い値に戻す。記録には接続の切れ目を書いていないので、読む側はそれを除けない
- スナップショットは上下 200 本までなので、それより外側の板は差分でしか分からない

## 書き込み

- 受信した行はファイルごとにメモリに溜め、`flushIntervalMs` (既定 5000) ごとに gzip して 1 回の追記で書く。プロセスが落ちて失うのはおよそこの間隔ぶん
- 既にあるファイルに書き足さないのは、追記の途中で落ちた末尾の後ろに書くと、普通の読み手 (`zcat`) がその先を全部読めなくなるため。プロセスごとにファイルを分ければ、壊れるのはそのファイルの末尾だけで、手前のメンバーと他のファイルは読める
- ファイルは排他作成 (既にあれば失敗) で作る。同じ名前があれば書き込み失敗として止まる。止まっても再起動で新しい名前になる
- 末尾が壊れたファイルを読めるのは、メンバーを順に展開して壊れた箇所で止まる読み手 (`zcat` / Python の gzip)。Bun / Node の `gunzipSync` はファイル全体を 1 回で展開し、末尾が壊れていると何も返さない
- `stop()` は溜まっている分を書いてから終わる。2 回呼んでもよい
- 生テキストに改行 (CR / LF) が含まれていたら空白に置き換える。JSON の文字列の中に生の改行は入らないので、置き換わるのは JSON の空白だけで意味は変わらない
- 日付の切り替えは受信時刻で決める (書き込んだ時刻ではない)
- 書き込み (ディレクトリ作成 / 追記) に失敗したら、捨てた行数と一緒に stderr に出して `onFatal` を呼び、記録を止める。CLI は exit 1。再試行はしない

## 受け付けるメッセージ

- 次のどちらかの形だけを書く。どちらでもないものは書かず、生テキストの先頭 200 文字 (改行は空白に置き換える) を含めて stderr に 1 行出す
  - `orderbook`: 長さ 2 の配列で、1 つ目が pair の文字列、2 つ目が object (配列と null は除く)
  - `trades`: 空でない配列で、要素がすべて配列であり、その 3 つ目 (pair) がすべて同じ文字列
- pair は `^[a-z0-9_]+$` に当てはまること (ファイルのパスに使うため。`../` などで `--out` の外に書かせない)
- 購読していない組でも、形が合えば書く

## 回復

- 再接続の待ちは 1s から倍々で最大 60s。有効なメッセージを 1 件受け取ったら 1s に戻す
- 切断 (close / error) でも無通信でも、再接続は 1 本だけ予約する
- 無通信: 接続を始めてから、または最後の有効なメッセージから 60 秒経ったら、その接続を捨てて再接続する。捨てた接続の close イベントは待たない。無効なメッセージは無通信の判定を延ばさない
- 無通信は接続全体で見る。板が流れている間に約定の stream だけが止まっても再接続はしない
- `--channel trades` だけの購読では、閑散時に 60 秒無通信で切るたびに再接続の待ちが伸び (最大 60 秒)、その間の約定を失う。btc_jpy の約定は 120 秒に 1 件の時間帯がある (2026-10-18 の観測)。約定を取るなら板と一緒に購読する (既定)。板は約 2.8 件/秒届くので切れない
- 60 秒ごとに stream ごとの起動からの累計件数を stderr に 1 行で出す (`stats orderbook/btc_jpy=1234 orderbook_snapshot/btc_jpy=5 trades/btc_jpy=0` の形)。購読している stream は 0 件でも出す
- 購読コマンドは接続を開いたら続けて全部送る。Coincheck の公式ドキュメントに購読の頻度の制限は書かれていない (2026-10-18 確認)

## やらないこと

- 注文・Private API
- 過去の約定の取得 (REST の `/api/trades` は最新分しか返さない)
- 板の組み立て・正規化 (記録は生のまま。組み立ては読む側でやる)
- 末尾が壊れたファイルの修復
